# xhs-guard —— 发布前审核

这是整个仓库的**强制关卡**。见 `AGENTS.md` 第 2 节：任何时候你把一段准备发布的
中文文案交给用户之前，必须先跑完这个技能，即使她没提合规。

---

## 核心立场：改主张，不改拼写

网上大量「违禁词替换」教程教的是：`最好` → `zui好`、`绝对` → `jue对`、
中间插空格或 emoji。**本技能禁止输出这类建议。** 三个原因：

1. 平台对变体词、谐音、拼音、形近字的识别早就上线了，绕不过去；
2. 「刻意规避审核」是独立的违规项，罚得比原违规更重；
3. 《社区公约 2.0》的核心是「真诚分享」，规避检测与之直接冲突。

正确的改法是**换掉那个站不住的主张**：

| ❌ 违规 | ❌ 伪装（更糟） | ✅ 正确 |
|---|---|---|
| 最好吃的一家 | zui好吃的一家 | 我今年去了三次的一家 |
| 100% 出片 | 100%出片✨ | 我拍了 40 张，有 6 张我挺喜欢 |
| 皮肤变白了 | 皮肤变⚪了 | 我自己觉得暗沉没那么明显了 |
| 必去 | b必去 | 如果只有一天，我会先去这里 |

区别在哪：右列是**可验证的个人事实**，左列是**无法举证的宣称**。

## 四层等级

| 等级 | 含义 | 处理 |
|---|---|---|
| 🛑 L1 硬红线 | 笔记删除 / 禁言 / 限制功能 / 封号 | **必须**删改，不可放行 |
| 🔴 L2 高风险 | 大概率判违规或直接限流 | **必须**改写 |
| 🟠 L3 中风险 | 取决于语境 | 逐条判断，多数需软化 |
| 🟡 L4 压流量 | 不违规，但拉低推荐/点击 | 建议优化 |

L1/L2 是**拦截项**（脚本 exit 1）。有拦截项时，不要说「可以发了」。

## 执行步骤

### 第 1 步 · 定位要审的文本

审核范围包括**标题 + 正文 + 标签 + 封面上的文字 + 视频口播稿**。
标签和封面文字一样会被审核，很多人只审正文，这是常见漏洞。

如果内容还没落盘，先写到 `drafts/<日期>-<slug>/note.md`，用这个格式：

```
---
title: 京都下雨那天我什么都没干
tags: [京都旅行, 一个人旅行, 雨天]
---
正文第一段……

正文第二段……
```

### 第 2 步 · 跑扫描器（确定性层）

```bash
python skills/xhs-guard/scripts/xhs_scan.py drafts/<日期>-<slug>/note.md
```

其他用法：

```bash
# 科普/清单型 —— 正文长度的舒适区和生活型不一样，一定要指定
python skills/xhs-guard/scripts/xhs_scan.py note.md --type guide

# 直接扫一段话
python skills/xhs-guard/scripts/xhs_scan.py --text "全网最好吃的一家，私我拿地址"

# 只看 L1/L2/L3，忽略 L4 优化建议
python skills/xhs-guard/scripts/xhs_scan.py note.md --min-tier L3

# 把 L3 也当拦截项（重要账号/商业合作稿建议加）
python skills/xhs-guard/scripts/xhs_scan.py note.md --strict

# 给程序用的 JSON
python skills/xhs-guard/scripts/xhs_scan.py note.md --json
```

Windows 上 `python` 不通就换 `py -3`。脚本只用标准库，不联网，不上传内容。

退出码：`0` = 无拦截项，`1` = 有拦截项，`2` = 参数/文件错误。

### `--type` 要选对

只影响**正文长度**的舒适区判断，但选错会给出没意义的建议：

| `--type` | 舒适区 | 用于 |
|---|---|---|
| `life`（默认） | 300–600 字 | 生活、日常、vlog、旅行片段 |
| `guide` | 400–950 字 | 科普、法规解读、清单、攻略、干货 |
| `short` | 80–300 字 | 一句话笔记 |

和 `xhs-note` 第 0 步定的模式保持一致。

### 第 3 步 · 语境裁决（模型层）★ 不要跳过

**扫描器负责召回，你负责精度。** 它是纯正则，不懂语境。
比如它会把「最好提前订票」和「最好用的防晒」都命中「最好」——
前者是建议语气，完全安全；后者是绝对化宣称，必须改。

逐条命中都要判断，重点看这几种情况：

- **建议语气 vs 宣称**：`最好+动词` 通常安全，`最好+形容词` 通常要改
- **自述 vs 因果绑定**：「我在减肥」安全；「喝这个瘦了五斤」要改
- **引用 vs 主张**：「老板说这是最好的」比自己说稍轻，但仍建议改
- **反讽/叙事**：「骗子让我加微信」是反诈叙事，不是导流
- **中文子串误伤**：词库已用 `exclude` 排除了 `平安神宫`/`治愈系`/`避雷针`/
  `特效镜头`/`永久性` 这类，但一定还有漏网的。遇到明显误伤，**放行并告诉用户
  你为什么放行**，同时建议把这个词加到 `lexicon.json` 对应规则的 `exclude` 里。

裁决结论只有三种，每条都要给：**必须改 / 建议改 / 误报放行**。

### 第 4 步 · 给改写方案，不只给问题

每个「必须改 / 建议改」的项，给出**具体的替换句**，不要只说「建议修改」。
改写时守住 `profile/voice.md` 的语气 —— 合规不是让她变成另一个人说话。

参考 `references/safe-rewrites.md` 的对照表。

### 第 5 步 · 改完重扫

```bash
python skills/xhs-guard/scripts/xhs_scan.py drafts/<日期>-<slug>/note.md
```

必须跑到没有 L1/L2 才算过。改一次不够就再改。

### 第 6 步 · 落盘两个文件

**`compliance.md`** —— 审核报告：

```markdown
# 合规审核 · <标题>

扫描时间：2026-08-13 ｜ 词库版本：2026.08.1
结论：✅ 已通过（0 个 L1 / 0 个 L2）

## 改了什么

| 原文 | 命中 | 等级 | 改成 | 为什么 |
|---|---|---|---|---|
| 最好吃的一家 | 最好吃 | 🔴 L2 | 我今年去了三次的一家 | 绝对化用语，无法举证 |
| 私我拿地址 | 私我 | 🛑 L1 | 店名写在图三了，直接搜就有 | 站外导流，执法最严的一类 |

## 判为误报、已放行

| 命中 | 为什么放行 |
|---|---|
| 安神（平安神宫） | 地名子串，与功效宣称无关 |

## 还需要你自己确认

- [ ] 图片里有没有其他平台水印
- [ ] 正文主要由 AI 起草 → 发布页勾【笔记含 AI 合成内容】
- [ ] 有对价 → 走蒲公英报备
- [ ] 人均 380 这个价格是最近核实的吗
```

**`checklist.md`** —— 发布前逐项确认，用 `references/publish-checklist.md` 作模板。
**不要替用户打勾**，尤其 AI 声明那条。

## 脚本查不了的（每次都要口头提醒）

扫描器只看文字。这几项必须人工过：

1. **图片/视频里的字**也会被审核 —— 封面文字、截图里的微信号、水印
2. **其他平台水印**（抖音/快手/B站 logo 或 ID）→ 判搬运，很确定会限流
3. **他人隐私** —— 正脸（尤其小孩）、车牌、门牌号、证件、登机牌
4. **AI 声明** —— 正文主要由 AI 起草，去发布页勾
   【设置】→【内容类型声明】→【笔记含 AI 合成内容】
5. **商业合作报备** —— 有任何对价（钱/免费/置换/返现）必须走蒲公英
6. **时效信息** —— 价格、营业时间、签证政策，重新核实一遍
7. **标签一次选对** —— 有流量后再改容易限流

## 词库维护

`scripts/lexicon.json` 是经验性清单，**不是官方词表**。平台规则在变
（《社区公约 2.0》2026-01、AI 内容治理规则 2026-04），词库会过期。

- 命中 ≠ 一定违规，未命中 ≠ 一定安全。要在报告里说清楚这一点，不要给虚假的安全感。
- 用户被限流但扫描器没报 → 把实际原因补成新规则，更新 `version` 和 `updated`。
- 误报 → 加到对应规则的 `exclude` 数组。
- `updated` 距今超过半年 → 主动提醒用户该复核平台最新规则了。

规则字段说明见 `references/platform-rules.md`。
